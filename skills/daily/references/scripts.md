# Scripts and files

`SKILL.md` points here. This is the inventory of what the skill ships: every script, the flags it
parses, and what each is for. `skills/daily/tests/test_references.py` holds the entries to
equality with the flags the scripts parse, so a flag added to a script wants an entry here.

## Files in this skill

- `SKILL.md` — the instructions a run loads first
- `.env.example` / `.gitignore` — Harvest credential template (copy to `.env`, gitignored)
- `references/first-run.md` — first-run setup: the screenshot task's health check (standing one up is the `setup` skill), `.context.md` creation, Harvest creds, AW discovery, AW category maintenance
- `references/context.md.example` — starter template for `Timesheets/.context.md`
- `references/classification-rules.md` — client/project/**work kind** rubric: the signal hierarchy, work kind and task selection, billing conventions, note style, exclusions. Read at Step 2 on every run
- `references/disambiguation.md` — what Step 5 does with a 🔸: the zoom → calendar drill-down → screenshots → ask ladder and its subagent brief, and the interleaved-day switch-point protocol. Loaded on a day that flagged something, or one shared between clients; what *raises* a flag is the rubric's, above
- `references/activitywatch.md` — raw AW API reference (endpoints, buckets, heartbeat dedupe, lock-screen quirk)
- `references/output-format.md` — what the timesheet .md holds, and its conventions
- `references/catalog-refresh.md` — refreshing `.mcp/` catalogs
- `references/new-client-work.md` — billing work that has no project yet (creating the work item, by the convention in `.context.md`)
- `references/reporting-issues.md` — reporting a defect upstream when the user installed this skill rather than maintaining it: the repo, what to redact first, and the confirmation gate before filing
- `docs/CONTRIBUTING.md` — in the repository, not in an installed copy: **for changing this skill, not for running it.** Start there before editing `SKILL.md`, a reference or a script. Ignore it on a normal run.
- `docs/skills/daily/decision-log.md` — the evidence behind the rules, and where a new finding about the skill goes rather than into `SKILL.md`.
- `scripts/afk_blocks.py` — deterministic day skeleton: work_start/work_end/breaks/active spans/active_ratio; `--window`, `--json`, `--utc-offset`, `--cover "HH:MM-HH:MM,..."` coverage check, plus the `## Preferences` tunables `--afk-threshold`, `--solid`, `--blip-gap`, `--min-uncovered`, `--active-band`, `--thin-band`
- `scripts/activity_timeline.py` — categorized window timeline + rollup; `--window HH:MM-HH:MM` zoom folds in web watchers; flags `uncategorized`/`!MULTI`; `--utc-offset`, `--json`, `--noise-floor`, `--gap-fold`, plus the two that control how much of the day you get back: `--full` shows every merged span, and `--min-span` sets the shortest span the compact default prints in minutes (`--min-span` is the `## Preferences` tunable `references/context.md.example` maps onto). Hidden spans are still counted in the per-category rollup, so the totals do not move
- `scripts/checkin_answers.py` — what the user said they were doing, read-only: one day, this host, from the check-in watcher (`aw-watcher-ask-away_<host>`, one event over the away gap, `data.message`) and the ask watcher (`aw-watcher-ask_<host>`, unanswered prompts dropped), each answer clipped to the day and printed as JSON in the skeleton's clock notation with a `status` of `ok`, `empty` or `absent`. An answer is context, never a block (ADR-0009). Given the day's other readings as files it classifies each answer (personal, one client, several, no client; a personal word always wins) and places it: a work answer over a break is a **question** (never a block, never drafted), a shorter gap or an ask answer is a **hint**, an answer inside a corroborated calendar block is context only. `--terms <file>` (clients' terms, the user's exclusions, `off`), `--skeleton <file>` (the skeleton as JSON), `--calendar <file>` (`calendar_day.py`), `--rulings <file>` (`Timesheets/<date>_harvest_responses.json`; a ruled question is listed under `ruled`, not `questions`). `--probe checkin|ask` (setup's check: is this host's watcher bucket there, and its newest event) and `--diagnose` (names the two-AFK-bucket condition that stops the check-in watcher, which bucket is stale, and the fix: export first, delete only on a yes naming it; it deletes nothing itself) take no date. Refuses like the day-reading scripts when ActivityWatch is unreachable; writes nothing. `--utc-offset` as the day-reading scripts take it
- `scripts/category_rules.py` — the activity source's **category rules**: gate, back up, write, verify (#69). `--from-context` reads each client's `**Client name**` and `**Category terms**` lines from `Timesheets/.context.md` — the one home of the terms; `--adopts Client=Existing` names a rule to replace — and `--candidates` takes `{client, terms}` objects, optionally `adopts`, from a file or stdin. It chooses no terms itself. Each client's terms become one rule, matched literally and without case in the app name or the title, each field on its own as the activity source matches them. The gate refuses a client with no terms or more than eight, and a term matching more than `--max-share` of the sampled window titles (0.35 by default); a refusal anywhere writes nothing, since the rule set is written whole. A term that matches none of them is written and reported `UNVERIFIED`, `dormant` or `suspect`, and two clients matching the same titles is reported `OVERLAP`. The clients' rules are written in the candidates' order, above the rules this plugin did not author. The previous rule set is backed up into `<workspace>/.mcp/` before the first write, which is the recovery path. The managed set is regenerated whole — a client missing from the candidates has its rule removed and the run says `DROPPED` — while the user's own rules are kept as they were unless a candidate names one in `adopts`. It reads the rules back and asks the activity source what each labels before recording what it wrote, so a write that did not land, or a rule the activity source does not match, stays `STALE`. `--days` sets the sample's span (7) and `--workspace` where the backup and the stamp go. `--inspect` lists the rules the activity source holds — `[managed]`, `[unmanaged]`, or `EDITED` for a managed one changed since it was written — each with its share of the sample and an example match, which is the read an adoption is made from, a `SEEN` line per profile tag in the titles, which `--candidates` also prints under an unverified term, and a `HOST` line per address the browser titles carry — a shared host such as `dev.azure.com` only with its organisation; `--status` says whether the rules are current for `Timesheets/.context.md`, from two local files, or `BROKEN` for rules an older version wrote. `--data-days` (with `--min-days`, 5 by default or the `Workdays before the category stage` line under `## Preferences`) prints one `DATA` line — recorded workdays (a weekday with 30 minutes of window activity while the AFK watcher says present, over 30 days) against the threshold, `COLLECTING` with the date to come back or `READY` — and a `say:` line to relay as it stands; it reads only and writes nothing. `--dormant <date>` (with `--lookback`, 14 days, and `--utc-offset`) flags a rule that matched in the days before the date and matches nothing on it, through the activity source's own `categorize`; it writes nothing. The module docstring carries the reasoning behind each of these
- `scripts/aw_client.py` — shared ActivityWatch REST helpers behind `afk_blocks.py`, `activity_timeline.py` and `calendar_day.py`, plus the server address (`TIMESHEET_ACTIVITY_URL`) all of them need, the day's window-event fetch and its two refusals (unreachable, no window bucket) that the timeline and the calendar wrapper share, and the one copy of the noise floor and gap fold both read window events by. *When* a day is read is the next entry's, not this one's
- `scripts/timezone.py` — the zone a day is read in (`TIMESHEET_TIMEZONE`, or the machine's own zone where none is configured, labelled as derived) and the clock arithmetic that follows from it: the day's UTC bounds, the local-clock rendering and the range parsing behind the window and coverage flags above, and where on a date the clocks change. Not a script, and not either half's: the two reading scripts above and the provider's guard imports it too, and its conversions apply the offset in force at each instant rather than one read once for the day, which is what makes the day the clocks change 23 or 25 hours long instead of silently short
- `scripts/provider/bin/timesheet-provider` — the timesheet provider's one command (`docs/provider-contract.md` is the specification), run by path as `python "<daily>/scripts/provider/bin/timesheet-provider" <post|patch|lookup|list|refresh>`. The dispatcher behind it holds the confirmation gate once, the argument validation and the adapter selection (`TIMESHEET_PROVIDER`, `harvest` when unset); the Harvest adapter is `scripts/provider/harvest/`, and everything Harvest-shaped — endpoints, field names, credentials, catalog files, the daylight-saving guard — stays inside it. `post --project-id ID --task-id ID --date YYYY-MM-DD --start HH:MM --end HH:MM --notes TEXT` and `patch ENTRY_ID` (with any of those flags, at least one) write only with `--confirm` and print `WOULD POST` / `WOULD PATCH` and the body without it; both refuse an entry that runs straight through a daylight-saving change, which Harvest would bill short by the repeated span — Step 9 has what to do with that refusal, and `patch` judges the entry it would *result* in. There is no duration flag: change a duration with `--start` and `--end`. `lookup QUERY` finds a project and its tasks across the whole catalog by code, project name **or client name**, with `--task`, `--json`, `--cache-only`, `--days` and `--catalog-dir`, and falls back to the user's recent entries for an archived project (exit 6 after the fallback = genuinely unknown project; a refresh won't help). `list FROM [TO]` lists the caller's own entries, and `--by-day` collapses it to one row per date — total, entry count and project codes, empty dates included; that is the month sweep the `reconcile` skill runs, and it is also the cheapest way to see a fortnight's gaps at Step 1. `refresh` rewrites the catalog `lookup` reads and prints `OK <n> projects`; `refresh --wait CODE` (with `--attempts` and `--delay`) polls for a just-created project and exits 6 if it never appears; `refresh --age` prints `AGE <days>` or `ABSENT` and touches nothing. Exit codes: 0 success or preview, 1 internal, 2 usage, 3 missing configuration, 4 refused, 5 unreachable, 6 no match
- `scripts/calendar_day.py` — the calendar wrapper (ADR-0008): one day's calendar events from whichever adapter is configured, filtered to what counts (accepted, organised or tentative — or never responded to, when the machine saw the meeting; busy or tentative; timed; not cancelled; starting on the day in the configured zone), as JSON in the skeleton's clock notation, with every event the day held and the filter removed listed under `dropped` with its reason — a calendar filtered to nothing is never an empty one. Each event carries its **corroboration verdict**: `corroborated` is true when at least a minute of meeting window from the activity source falls inside it — a `Meeting | …` / `Call with …` title, or a Teams window whose first segment (or the one after `Meeting join |`) is the event's own subject — and the event then carries the `evidence` span seen and a proposed `block` span — the event, extended to the end of the evidence when the meeting ran over; an uncorroborated event carries neither. Refuses like the two day-reading scripts when ActivityWatch is unreachable. Runs only when `TIMESHEET_OUTLOOK_CALENDAR` is `true` and exits non-zero saying so otherwise; an adapter that cannot read the calendar is a non-zero exit with its reason, never an empty day. `--utc-offset` as the day-reading scripts take it; `--noise-floor` and `--gap-fold` as the timeline takes them; `--min-evidence <seconds>` moves the one-minute floor; `--adapter <path>` runs another adapter (a test's fake) in place of the configured one, which is the next entry. `--detail <id>` prints one event's body and location in place of the day — Step 5's drill-down, reading nothing else. What a run does with the verdict is Steps 2, 3 and 6
- `scripts/outlook_calendar.ps1` — the configured calendar adapter: reads the **default calendar only** in classic Outlook through its COM object model (Windows only; starts Outlook in the background if it is not running, never closes it) and prints the raw calendar day in the wrapper's contract — recurring meetings as the day's instances, basic fields only (subject, start, end, show-as, response, all-day, cancelled, attendee names; no body, no location, rooms dropped). An appointment the user wrote themselves is reported as `organizer`. No classic Outlook, or no default calendar, is a non-zero exit with a one-line reason the wrapper passes on. Not run directly: `calendar_day.py` runs it under Windows PowerShell 5.1 when the toggle is on
- `scripts/skill_config.py` — the seam every script reads a setting through; its docstring carries the flag / `.env` / environment / default precedence and the reasoning behind it
- `scripts/refresh_catalogs.py` — refresh the work-item catalog through the work-item source boundary (`scripts/work_items/`; the adapter and every account fact come from `.context.md` § "Work-item source"); it takes no flags, and the provider's own catalog is `timesheet-provider refresh`, not this script's
- `scripts/screenshot_capture.py` (`--where`) + `scripts/setup_screenshot_pipeline.ps1` — per-monitor capture + one-time scheduled-task setup. `--where` prints the resolved capture directory and captures nothing; it is how you get that path for a PowerShell command, per "Screenshot location" above
- `tests/` + `pytest.ini` — the script suite. Maintainers only; `docs/CONTRIBUTING.md` explains what it does and does not measure.
